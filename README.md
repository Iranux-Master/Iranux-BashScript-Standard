# Iranux Bash Script Standard

**A lightweight, self-contained metadata and verification standard for Bash scripts executed through Iranux.**

> Status: Draft v1.1  
> Target: Bash scripts executed remotely through the Iranux Windows application  
> Scope: metadata, parameter discovery, form generation, UI library organisation, compatibility validation, embedded certification, and final-marker detection

## What changed in v1.1

Iranux Bash Script Standard v1.1 adds required UI library metadata for scripts that declare schema version `1.1`:

- `ui.category`
- `ui.action`
- `ui.icon`

These fields allow Iranux to organise scripts by operating system, category, and action group, and to render every script as a labelled button with a valid Material Design Icon.

Version 1.1 is backward-compatible at the application level:

- scripts declaring `schema_version: "1.0"` continue to follow the v1.0 rules;
- scripts declaring `schema_version: "1.1"` must satisfy all v1.1 requirements;
- no v1.0 field or block syntax has been removed.

## Core design philosophy

The standard is a metadata and tagging standard. It is not a Bash framework, workflow engine, package manager, SSH protocol, configuration-management system, or replacement for Ansible or cloud-init.

The standard describes:

- what a script does;
- what user inputs it requires;
- how those inputs should be presented;
- which operating systems and commands it requires;
- how the script is grouped in the Iranux library;
- which MDI icon Iranux should render;
- whether the script is Compatible or Verified;
- whether execution reached the intended final point.

The application execution layer remains responsible for parameter transport, SSH execution, streaming, shell escaping, cancellation, timeouts, and result presentation.

## Script status levels

### Plain Bash Script

A script without Iranux metadata. Iranux cannot automatically discover structured parameters or UI metadata.

### Iranux Compatible

A script with valid `IRANUX_METADATA` and zero or more valid `IRANUX_PARAM` blocks. For schema v1.1, valid `ui.category`, `ui.action`, and `ui.icon` fields are also required.

### Iranux Verified

An Iranux Compatible script with a valid `IRANUX_CERTIFICATION` block generated by the official deterministic Iranux Validator. Script authors and AI tools must never create or alter certification blocks.

## Official block syntax

### Metadata block

Exactly one metadata block is allowed:

```bash
: <<'IRANUX_METADATA'
{
  "standard": {
    "name": "iranux-script-metadata",
    "schema_version": "1.1"
  },
  "script": {
    "id": "test-remote-port",
    "name": "Test Remote Port",
    "version": "1.0.0",
    "description": "Tests whether a TCP port is reachable on a remote host."
  },
  "risk": {
    "level": "safe"
  },
  "requirements": {
    "requires_root": false,
    "requires_internet": true,
    "supported_os": ["ubuntu", "debian"],
    "required_commands": ["nc"]
  },
  "ui": {
    "category": {
      "id": "network",
      "name": "Network and IP"
    },
    "action": {
      "id": "network-diagnostics",
      "name": "Network Diagnostics"
    },
    "icon": {
      "library": "mdi",
      "name": "lan-connect"
    }
  }
}
IRANUX_METADATA
```

### Parameter block

Each input is described by a separate block:

```bash
: <<'IRANUX_PARAM'
{
  "name": "remote_port",
  "label": "Remote Port",
  "description": "The TCP port to test.",
  "type": "port",
  "required": true,
  "default": 443,
  "example": 22,
  "placeholder": "443",
  "group": "Connection"
}
IRANUX_PARAM

REMOTE_PORT="${REMOTE_PORT:-443}"
```

### Certification block

At most one certification block is permitted. It may be generated only by Iranux Validator.

```bash
: <<'IRANUX_CERTIFICATION'
{
  "standard": "iranux-certification",
  "version": "1.0",
  "status": "verified"
}
IRANUX_CERTIFICATION
```

## Required v1.1 metadata

Every v1.1 metadata block must contain:

```text
standard.name
standard.schema_version
script.id
script.name
script.version
script.description
risk.level
ui.category.id
ui.category.name
ui.action.id
ui.action.name
ui.icon.library
ui.icon.name
```

`standard.name` must be `iranux-script-metadata` and `standard.schema_version` must be `1.1`.

## Category and action rules

Category is the primary library grouping. Action is the functional subgroup inside a category.

```json
"ui": {
  "category": {
    "id": "software-installation",
    "name": "Software Installation"
  },
  "action": {
    "id": "web-servers",
    "name": "Web Servers"
  }
}
```

Identifier rules:

```regex
^[a-z][a-z0-9-]*$
```

IDs must not include numeric folder prefixes. Use `network`, not `04-network`.

Names are human-readable English labels. Scripts sharing the same category or action ID must use the same corresponding name.

## MDI icon rules

Every v1.1 script must declare one MDI icon:

```json
"icon": {
  "library": "mdi",
  "name": "dns"
}
```

Rules:

1. `library` must be exactly `mdi`.
2. `name` must use the canonical Pictogrammers Material Design Icons name without the `mdi-` prefix.
3. The name must match `^[a-z0-9]+(?:-[a-z0-9]+)*$`.
4. Iranux Validator must verify that the name exists in the official MDI catalogue used by the validator.
5. A v1.1 script with a missing or unknown icon is invalid.
6. Iranux should render the validated icon name on the script button.
7. As a defensive UI fallback only, the application should render `script-text-outline` when an icon cannot be resolved at runtime. The fallback does not make invalid metadata valid.

Official icon library:

https://pictogrammers.com/library/mdi/

The standard stores only the canonical icon name. It does not store codepoints, CSS classes, font files, or package-version-specific enum names.

## Risk levels

Allowed values:

```text
safe
low
medium
high
dangerous
```

Typical interpretation:

- `safe`: read-only or informational;
- `low`: minor low-impact change;
- `medium`: package installation or service change;
- `high`: SSH, firewall, users, permissions, networking, or critical services;
- `dangerous`: destructive or highly disruptive operation.

## Requirements metadata

Optional requirements help Iranux explain compatibility before execution:

```json
"requirements": {
  "requires_root": true,
  "requires_internet": true,
  "supported_os": ["ubuntu", "debian"],
  "required_commands": ["apt-get", "systemctl"]
}
```

## Parameter rules

Each `IRANUX_PARAM` block requires:

```text
name
label
description
type
required
```

Optional fields:

```text
default
example
placeholder
group
sensitive
options
validation
```

Parameter names must match:

```regex
^[a-z][a-z0-9_]*$
```

Supported v1 parameter types:

```text
string
multiline
int
float
bool
enum
multi_select
password
secret
port
email
url
domain
hostname
ip
ipv4
ipv6
cidr
mac
path
date
time
datetime
duration
size
cron
json
ssh_public_key
private_key
certificate
```

Use `enum` when the Bash logic expects exact values such as `Y`/`N`, menu numbers, or named modes. For `enum` and `multi_select`, `label` is shown to the user and `value` is supplied to the script.

Sensitive types include `password`, `secret`, and `private_key`. Iranux must mask these values and exclude them from logs, previews, history, reports, and error details.

## Non-interactive normal path

Iranux Compatible scripts should obtain declared values from variables populated by the application execution layer:

```bash
DOMAIN="${DOMAIN:-example.com}"
```

The standard intentionally does not define whether the execution layer uses environment variables, arguments, stdin, or another safe transport. Interactive `read` prompts should not be required in the normal Iranux execution path.

## Final execution marker

Every Compatible or Verified script must print the following marker only on the successful normal path:

```bash
echo "__IRANUX_REACHED_END_V1__"
```

Place it immediately before a final successful `exit 0` when one is present. The marker means only that execution reached the intended final point. It does not independently prove that every operation succeeded.

## Validator responsibilities

Iranux Validator performs deterministic validation and certification:

- parse all Iranux blocks;
- validate strict JSON;
- validate schemas and required fields;
- validate IDs, parameter names, types, options, defaults, and duplicates;
- validate category and action consistency;
- validate MDI icon syntax and existence;
- verify the final marker;
- compute the certifiable-content hash;
- generate and sign `IRANUX_CERTIFICATION`.

AI tools may produce Compatible candidates but must not verify, certify, sign, or generate `IRANUX_CERTIFICATION`.

## Application responsibilities

Iranux Runner/App performs lightweight runtime work:

- detect Plain, Compatible, and Verified scripts;
- read metadata and parameters;
- filter by supported operating system;
- group by category and action;
- render the script name and MDI icon as a button;
- build and validate the user form;
- mask sensitive values;
- verify certification for Verified scripts;
- execute remotely;
- stream output;
- inspect the process exit code;
- detect the final marker.

For implementation by an AI coding agent, use the deterministic flow in `docs/implementation/ai-app-integration-guide.md`.

## Compatibility policy

- v1.0 documents remain valid under the v1.0 schema.
- v1.1 documents require the complete `ui` object.
- A v1.0 document must not be silently treated as v1.1.
- Unknown future schema versions should be rejected or handled through an explicit compatibility policy.
- The final marker remains `__IRANUX_REACHED_END_V1__` because marker versioning is independent of metadata schema versioning.

## Out of scope

The standard does not define:

- parameter transport strategy;
- SSH session implementation;
- remote upload strategy;
- shell escaping implementation;
- output streaming protocol;
- rollback;
- multi-step workflows;
- dependency graphs;
- structured final result JSON;
- post-install success checks.

These belong to the Iranux execution layer or future implementation documents.
